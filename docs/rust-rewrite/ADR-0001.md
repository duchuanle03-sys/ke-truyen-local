# ADR 0001: staged Rust backend migration

Date: 2026-11-16. Status: accepted for M1 by the user; later milestones require separate approval.

## Decision

Replace the Python backend and Node.js STV transport with one Rust backend package under `rust/`, initially a library plus a binary with domain modules. Keep `web/app.js`, `web/reader.js`, `web/captcha.js`, `web/index.html` and `web/style.css` byte-for-byte unchanged. There is no Rust/WASM frontend work. Preserve HTTP requests, responses, localized errors, storage semantics and user workflows.

This checkout is already an isolated linked worktree on `rust-rewrite`; the main checkout remains separate. The Python/Node sources and existing tests are immutable reference inputs until the full parity/cutover gate. `Start.cmd` stays unchanged during migration. Preparation creates documentation only; the disposable, standard-library-only MSVC probe is outside the repository.

## Alternatives considered

- **Single Rust package, domain modules (recommended):** small interface surface, one dependency graph, straightforward end-to-end tests. Split crates only when an actual independent consumer or build requirement appears.
- Multiple crates immediately: stronger package boundaries, with additional manifests and cross-crate interfaces before their usefulness is established.
- Replace the running backend route by route through a Python/Rust proxy: enables early mixed operation, but introduces two owners of SQLite, caches, sessions and shutdown. Reject for this migration; use separate synthetic test instances until complete cutover.

The recommendation is an orchestrator proposal, not an already approved implementation choice.

## Boundaries

`http` owns routing, guards, request decoding, safe output and response semantics. `library`, `chapters`, `assets`, `search`, `qt`, `sources`, `downloads`, `documents`, `platform` and `lifecycle` own their existing domains. Handlers must not contain storage or scheduling policy. SQLite, HTML parsing, OCR and slow filesystem work run outside asynchronous HTTP executor threads and outside long database transactions/shared asset locks.

Start with ordinary modules, not traits/wrappers for hypothetical backends. M1 selects Hyper/Tokio for HTTP, serde/serde_json and bundled rusqlite; versions are pinned by `rust/Cargo.lock`. The initially tried tiny_http adapter was removed because rejected-body cleanup could block the server and allocate from an advertised body length. The selected Rust SQLite build must pass exact schema/FTS/JSON/function probes. A generic HTTP client has not demonstrated STV transport equivalence.

Persisted compatibility includes tables, indexes, triggers, generated columns, FTS shadow state, counters, pending work, resumable cursors and Unicode SQL functions. Register exactly compatible deterministic `shelf_fold`/QT folding functions on every relevant connection before preparing dependent statements. Preserve the reference Python Unicode version or explicitly prove an equivalent mapping; lowercase is insufficient. Do not rebuild persisted expression indexes under a different function.

Acquire the exclusive library lock and implement admission, cancellation and retryable drain before any operation that can write, including chapter/image GETs that update LRU or reader leases. Run only one production owner of a data directory. Rust must never launch the reference App against private data: its startup creates/upgrades schemas, recovers jobs, expires trash and starts workers.

The first slice is a fixture-only read-only shelf service. It does not claim to run the complete frontend. Later milestones add genuine bootstrap, reader, writers and maintenance behind their own gates. An isolated STV transport feasibility gate runs early so Windows/TLS incompatibility is discovered before cutover planning depends on it.

## Data and cutover

All preparation and differential fixtures are synthetic. Do not open, copy, hash, mutate or commit actual user databases, dictionaries, downloaded content, backups or private profiles. An oracle may use a disposable synthetic copy; a Rust integrity test uses a different finalized copy. Never initialize the reference App on the fixture whose unchanged hash is being asserted.

Do not use `immutable=1` to bypass WAL handling on a potentially active database. Read-only failures must remain failures, with no writable fallback. Before a writable milestone, freeze a schema fingerprint and SQL-function compatibility contract. Schema-changing upgrades require interruption/recovery tests and a documented downgrade boundary. Rollback after new writes is allowed only if the old reader can safely consume the resulting schema; otherwise restore a consistent stopped backup rather than mixing old SQLite/WAL files or silently downgrading.

Legacy retirement, launcher replacement and packaging happen only after all route/behavior gates, Windows integration, release performance, crash/restart and independent review pass. Final runtime must require neither Python nor Node. Existing PowerShell helpers may be invoked unchanged during intermediate milestones; declare their final packaging dependency before cutover.
